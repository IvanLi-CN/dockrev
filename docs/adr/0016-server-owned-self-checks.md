# 服务端拥有自检生命周期，网页按实际影响展示结果

Dockrev 的自检用于发现服务运行环境与功能配置问题。服务端启动后必须主动完成首轮自检，后续复查由服务端调度；网页访问不能决定自检何时运行，也不能把等待报告作为显示应用或允许操作的通行条件。

## 已收敛的需求

1. 每次服务端启动后主动执行一次启动自检，无论是否有浏览器访问。自检应结合启动阶段的发现结果，避免将发现尚未完成误判为配置故障。
2. 服务端负责启动自检和后续后台自检的调度、并发收敛、结果保存及状态发布。打开网页、刷新、新建标签页、切回前台或连接恢复可以读取现有结果，不能因此启动新一轮自检。
3. 普通读取自检结果不触发检查。手动“重新检查”可以明确请求服务端执行诊断，并展示该动作的局部反馈。
4. 网页加载和自检独立。正常、检查进行中、尚无报告、报告读取失败或连接暂时中断均不得产生整页自检等待，不得仅因此一概禁用更新、启停等操作。页面自身的数据加载仍由对应区域展示反馈。
5. 启动自检确认核心故障后，网页自动显示自检页。邮件、Telegram 等可选功能的配置问题只在相关功能或设置处提示，不触发全站自检页。
6. 自检页是诊断入口，必须提供明确的故障原因、影响、修复建议和手动复查，并保留继续浏览、前往设置或发现扫描等适用的修复入口。核心故障不等于锁死整个应用。
7. 后续后台自检应尽量安静。通过、进行中及未变化的结果不得重复弹窗、跳页、显示成功通知或覆盖现有内容。用户已进入正常页面后，后台自检新发现核心故障也保留当前页面，仅显示简短故障提示、提供主动打开自检页的入口，并限制确实依赖故障能力的操作；不得打断填写、排查或正在进行的浏览。
8. 故障分级、是否自动显示自检页、是否限制某项操作是三个独立判断。不能直接把现有报告的整体 FAIL 或 required 标记等同于全站阻断。
9. 具体操作的必要前提由服务端在操作边界校验。自检通过不能替代操作前置校验，前端没有读到报告也不能替代服务端对操作的实际判断。明确故障只影响依赖它的操作和对象；浏览、诊断与必要修复入口保留。
10. 既有身份鉴权独立执行。某个访问者的请求鉴权结果不能成为部署级后台自检的全局结论，未授权访问继续走既有鉴权处理。
11. 健康部署不得因“不再自动显示”偏好尚未设置而展示成功自检页。自检页可主动打开，健康状态不需要用户确认通过或重复跳转才能进入管理页面。
12. 服务端每 5 分钟执行一次后台自检，并在相关配置或发现结果变化时合并触发复查。没有相关变化的周期发现扫描不应触发额外复查；自检任务不并发重复执行，不因页面数量增加检查次数。运行期间收到变化时，应合并处理并保证最终结论覆盖这些变化。
13. 自检结果必须标明其属于哪次服务端启动及何时完成。持久化的旧报告可以作为带时间的诊断参考，但不能冒充当前启动已完成的首轮结论，也不能单凭旧报告强制跳页。进行中的复查不撤销最近一次已确认结论；临时探测异常与报告读取异常须与已确认能力故障区分。
14. 同一次服务端启动、同一个持续故障，对同一浏览器最多自动展示一次自检页。用户选择继续浏览后，刷新或新开标签页均只保留故障提示和对应操作限制，不再强制跳页；防重复展示状态须在同一浏览器的标签页之间共享。此规则不改变后台新故障不得打断当前页面的要求。

## 后续实现细则的边界

- 自动展示只取决于服务端确认的当前启动核心故障。后台复查结果只更新局部提示与相关操作状态；背景故障恢复后再发生，仍不能打断正常使用中的页面。
- 静态配置问题可以由明确诊断确认；临时命令超时、运行时连接失败需经服务端有界复核后再作为稳定故障对外发布。具体复核间隔、超时预算和任务合并方式由实现设计确定，但不得重新引入网页触发检查、无界重试或全站等待。
- 限制策略必须按故障能力和受影响对象明确映射。例如 Compose 执行器故障限制依赖 Compose 的变更，单个项目路径或镜像问题限制相关项目或服务；通知渠道配置问题不影响更新或启停。不得用报告整体 FAIL 代替此映射。
- 故障恢复应自动解除对应提示与限制，并保留用户当前页面；主动停留在自检页的用户可以看到更新后的结果并自行返回。恢复过程不显示成功弹窗或强制跳转。

## 验收场景

| 场景 | 必须满足的结果 |
| --- | --- |
| 服务端启动，无浏览器访问 | 服务端仍主动产生本次启动的自检结果 |
| 健康部署打开、刷新或新增网页标签 | 正常加载目标页面，不发起新的自检，不显示自检等待或成功欢迎页 |
| 网页恢复前台、事件连接恢复 | 可重读已有结果，不能由此启动自检或覆盖当前内容 |
| 无浏览器访问且距上一轮自检已满 5 分钟 | 服务端自主执行后台复查；多个网页同时读取结果不增加检查次数 |
| 相关配置或发现结果实际变化 | 合并触发复查；重复且未变化的发现结果不反复触发检查 |
| 首轮自检尚未完成或报告暂不可读 | 正常页面可展示；未知状态不冒充核心故障，也不单独成为操作禁用依据 |
| 服务重启后存在上一轮持久化报告 | 明确区分旧报告和当前启动结果，不因旧失败报告跳页或因旧通过报告冒充启动自检完成 |
| 启动自检确认核心故障 | 自动展示有原因和修复入口的自检页，允许继续浏览和前往修复入口 |
| 同一启动、同一持续故障，用户继续浏览后刷新或新开标签页 | 不再强制跳转自检页，故障提示与受影响操作的限制仍保留 |
| 同一浏览器的多个标签页遇到同一启动的同一持续故障 | 自动展示次数在标签页之间协调，总计最多一次 |
| 邮件或 Telegram 配置错误，核心能力正常 | 不自动进入自检页，只在对应功能或设置处提示 |
| 后台自检通过或结果未变化 | 无弹窗、跳页、遮罩和成功通知 |
| 正常使用中，后台自检新发现核心故障 | 保留当前位置与页面内容，简短提示并提供自检入口；仅限制受影响操作，不自动跳转 |
| 某项能力发生确定故障 | 仅限制依赖该能力的具体操作和对象，并说明原因；不阻塞无关浏览与修复 |
| 用户手动重新检查 | 服务端执行复查，反馈限于该动作，不切换全站加载态 |
| 故障经复查确认恢复 | 自动移除对应提示和限制，保留用户当前页面，不显示成功弹窗 |
| 自检结果通过，但操作前置条件随后变化 | 服务端在实际操作边界拒绝不满足条件的操作并返回具体原因 |

## 与现有实现和规范的冲突

- [App.tsx](../../web/src/App.tsx) 将入口初始状态设为 loading，读取报告并主动请求后台刷新；未通过时替换整页或强制跳转。该职责划分不符合本次需求。
- [报告读取接口](../../crates/dockrev-api/src/api/mod.rs) 在没有报告或报告超过有效期时自动排入检查；读取与触发检查需要解耦。
- [服务端启动入口](../../crates/dockrev-api/src/main.rs) 创建了自检 worker，但没有主动排入启动自检。
- 现有报告将部分已启用条件功能标记为 required，其失败会使整体结果成为 FAIL；[前端判定](../../web/src/deployCheck.ts) 又将整体 FAIL 当作阻断依据。不能直接沿用此结果制定新的展示和限制策略。
- [EdgeOne 主题规范](../specs/dh3i9-edgeone-origin-timeout-hardening/SPEC.md) 中“无缓存安全阻断”“页面启动或前台恢复发起复核”“新 required core FAIL 强制进入门禁”等约束与本次需求冲突，后续主题规范同步需明确更新；其他主题约束不受影响。

## 取舍

保留完整 Loading 页面只能改善反馈，仍让用户为服务端运维诊断等待。仅将浏览器触发的复查移到后台，仍会让标签页数量和访问行为决定服务端检查次数。自检由服务端拥有，并按实际影响展示结果，可以同时消除入口等待、重复检查与无关操作被阻断的问题。

本文记录已收敛的需求和职责决策，不包含执行计划；实现与验证状态由 `docs/specs/server-owned-self-checks/` 及其历史记录维护。
