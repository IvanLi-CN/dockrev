# Dockrev：服务资源监控 演进历史（#kbz3z）

> 这里记录会影响后续维护者理解“为什么如此设计”的关键演进；规范正文仍以 `./SPEC.md` 为准。

## Decision Trace

- 2026-07-20: 历史采样采用每个 compose project 独立固定 cadence、single-flight 与跳过过期 tick，避免单项目慢采集阻塞整站历史落库。
- 2026-07-26: 101 诊断确认 Docker metadata 路径卡顿时，普通命令超时会残留子进程，且实时与历史链路各自创建 Engine client，导致资源采集持续叠加压力。
- 2026-07-26: 锁定修复为 runner 超时终止子进程，以及实时/历史共享单一 Engine client 的固定 4 请求限流与熔断；不增加配置、API 或 UI。
- 2026-07-26: 审查发现半开探测取消会遗留半开状态；保护令牌的 drop 路径改为恢复带退避的打开状态，并由回归测试锁定。
- 2026-07-26: 审查发现已排队的请求若只等待并发令牌，会在熔断打开后继续被旧请求阻塞；限流等待改为监听熔断打开转换并立即降级，避免在 daemon 退化时延迟采样 worker。
- 2026-07-27: 101 基准显示 `stream=false` 在 Engine 中等待第二次 stats 快照，74 个容器会使 per-project 历史 worker 持续跨周期。采用 one-shot 原始读数和应用侧 CPU 基线，以一次全局容器发现服务历史与并发 SSE。
- 2026-07-27: 审查确认单项目 SSE 不得清除其它 compose project 的 CPU 基线；基线回收限定在当前发现批次，协调器同时驱逐过期空闲项目状态，并恢复单项目 Docker label 过滤以避免全量发现开销。
- 2026-07-27: 审查确认采集 future 取消会永久遗留项目 `in-flight`，且监控禁用期间完成缓存会长期驻留；协调器增加取消清理 guard、等待重试和禁用态缓存清理。
- 2026-07-27: 审查确认已删除 compose project 的 CPU 基线会长期驻留，且同步 GC 会阻塞全局采样 cadence；全局发现现在回收项目集合外基线，历史 GC 拆为独立后台任务。
- 2026-07-27: 生产库已有超过保留期的积压，因每小时仅删 10,000 行无法追上写入。保留期锁定为 24 小时，GC 改为启动后和每分钟的有上限分批排空；SQLite 文件压缩仍需独立维护窗口人工执行。

## Key Reasons / Replacements

- 全局协调优先于跨项目无缺样：健康状态下仍按既有频率采集，退化或过载时允许当前周期缺样且不补历史欠账。
- 4xx 容器生命周期竞争不代表 daemon 不可用，保留既有部分成功与局部失败语义；只将连接错误、超时、5xx 和无效成功响应计入熔断。
